# 授权链路安全审查与整改建议

**项目**: TLS-shipinhao  
**审查范围**: 桌面端授权主链路、授权服务客户端、云端授权服务、离线授权能力、任务级授权能力  
**审查日期**: 2026-04-17  
**审查视角**: 网络安全 / 产品安全 / 商业授权防护

---

## 1. 概述

当前项目已经具备较完整的授权体系雏形：

- 桌面端可执行激活、校验、状态读取
- 云端 Worker 已具备 `/api/activate`、`/api/verify` 路由
- `license-service` 已实现卡密、设备绑定、有效期、吊销等核心规则
- 本地已实现 Lease 验签、离线校验、续约接口抽象、任务级授权、完整性校验、安全存储等能力模块

但从产品安全与商业授权防护角度看，**当前主运行链路仍未完成“强授权闭环”**。最关键的问题是：

> 当前桌面端真正决定业务是否可执行的依据，仍然是本地明文 `license.json` 中的 `license_state`，而不是验签后的 Lease / RuntimeState。

这意味着：

- 本地授权状态存在被篡改风险
- 离线场景下存在绕过门禁的可能
- 已实现的密码学能力与完整性能力没有真正进入主执法链
- 服务端授权规则虽存在，但客户端可信执行链尚不完整

**总体判断**：授权后端设计方向正确，但客户端执法链未闭环，当前属于“安全能力已铺设、主链路未完全接入”的状态。

## 2. 当前授权链路摘要

当前主链路可概括为：

1. 前端输入卡密，调用 Tauri IPC：`activate_license` / `verify_license`
2. 桌面端采集 `device_id` 与 `device_fingerprint`
3. 通过 `http_license_client.rs` 请求云端授权服务
4. Worker 路由到 `license-service`
5. 云端返回 `license_state`、`license_expires_at`、`license_lease`
6. 桌面端当前仅提取并保存：
   - `license_key`
   - `license_state`
   - `license_expires_at`
   - `last_verified_at`
7. 后续业务功能通过 `ensure_feature_authorized()` 判断本地 `license_state` 是否为 `active/renewal_due`

当前真正参与业务门禁的关键对象是：

- `apps/desktop/src/state.rs` 中的 `StoredLicenseProfile`
- `apps/desktop/src/commands/license.rs` 中的 `ensure_feature_authorized()`

而不是：

- `backend/crates/license/src/local_verify.rs`
- `backend/crates/license/src/lease.rs`
- `apps/desktop/src/adapters/secure_storage.rs`
- `backend/crates/security/src/integrity.rs`

这正是当前安全短板的核心来源。

## 3. 审查结论摘要

### 总体安全评级

**评级：中等偏弱（6/10）**

### 结论摘要

- **服务端授权逻辑**：较完整，具备设备绑定、过期、吊销等规则
- **客户端展示与交互**：完整
- **客户端可信执法链**：不完整
- **离线授权闭环**：能力存在，但未接入主链
- **安全存储闭环**：能力存在，但未接入主链
- **完整性保护闭环**：能力存在，但未接入主链
- **任务级授权闭环**：能力存在，但未接入主链

### 关键判断

当前版本的核心问题不是“没有授权系统”，而是：

> **已有授权系统，但客户端仍主要依赖弱本地状态控制功能放行。**

## 4. 主要风险发现

---

### 4.1 高风险：本地明文 `license.json` 可被篡改，业务门禁可被绕过

**风险等级**: HIGH

#### 证据

- `apps/desktop/src/state.rs`
  - `load_license_profile()`：直接读取 `license.json`
  - `save_license_profile()`：直接写入 `license.json`
- `apps/desktop/src/commands/license.rs`
  - `ensure_feature_authorized()` 只判断本地 `license_state`
  - 放行条件为 `active | renewal_due | ok`

#### 风险说明

当前业务能力（评价查询、订单同步、发货等）是否可用，主要取决于本地缓存状态文件。如果攻击者能够修改本地 `license.json`，便可能将授权状态伪造成 `active`，从而绕过授权控制。

#### 影响

- 越权使用付费功能
- 吊销状态被本地覆盖
- 设备不匹配状态被本地覆盖
- 离线场景下脱离云端继续使用
- 商业授权模型失效

#### 整改建议

必须将业务门禁的信任根从：

- `StoredLicenseProfile.license_state`

改为：

- **验签后的 Lease / RuntimeState**

建议最终链路改为：

```text
本地密文 lease_token
 -> LeaseVerifier 验签
 -> 校验 device_id
 -> 校验 exp / renew_after
 -> 生成 RuntimeState
 -> 根据 RuntimeState 决定是否允许执行功能
```

---

### 4.2 高风险：客户端未真正消费 `license_lease`，密码学保护未落地到主链路

**风险等级**: HIGH

#### 证据

- `apps/desktop/src/adapters/http_license_client.rs`
  - `LicenseApiResponse` 已定义 `license_lease: Option<String>`
- `apps/desktop/src/commands/license.rs`
  - `activate_license()` / `verify_license()` 仅保存 `license_state`
  - 返回给前端的只是 `license_lease.is_some()` 布尔值
- 未看到主链路中：
  - 对 `license_lease` 验签
  - 对 `license_lease` 落库
  - 对 `license_lease` 离线校验
  - 对 `license_lease` 执行业务门禁

#### 风险说明

系统虽然已经设计了基于 Ed25519 的 Lease 授权模型，但客户端当前并未以它作为可信主对象。换言之，**安全模型已存在，执行模型未切换**。

#### 影响

- 服务器签发的强授权材料没有真正成为客户端信任基础
- 客户端授权判断仍依赖普通文本状态
- 安全收益远低于设计预期

#### 整改建议

激活与校验成功后，客户端应：

1. 要求服务端返回有效 `license_lease`
2. 客户端使用 `LeaseVerifier` 验签
3. 校验 `kind`
4. 校验 `device_id`
5. 校验成功后再落地本地安全存储
6. 后续门禁只使用验签结果，不再直接相信服务端返回的裸状态文本

---

### 4.3 高风险：安全存储模块已实现但未接入，授权主材料仍明文落盘

**风险等级**: HIGH

#### 证据

- 已实现：`apps/desktop/src/adapters/secure_storage.rs`
  - `KeychainSecretStore`
  - `EncryptedFileSecretStore`
  - `SecretStore` 抽象
- 但主授权链路当前实际使用：
  - `apps/desktop/src/state.rs` 中的 `license.json`

#### 风险说明

当前敏感授权材料没有进入系统密钥环或加密文件后备，而是以明文 JSON 的形式存在。对本地攻击者、恶意软件、共享终端、开发环境泄漏等场景来说，这会显著提升篡改与复制风险。

#### 影响

- 本地授权材料可被直接读取、复制、篡改
- 无法达到桌面商业授权常见的最小防护要求

#### 整改建议

将授权主存储切换为：

- 首选 `KeychainSecretStore`
- 回退 `EncryptedFileSecretStore`

同时建议：

- `license.json` 仅保留 UI 需要的弱缓存字段
- 真正的 `lease_token` / `runtime_bundle` 不应明文存盘

---

### 4.4 高风险：离线授权、续约、任务级授权、完整性能力未进入主执行链

**风险等级**: HIGH

#### 证据

以下能力已实现，但当前主链路未接：

- `backend/crates/license/src/local_verify.rs`
- `backend/crates/license/src/lease.rs`
- `backend/crates/license/src/task_grant.rs`
- `backend/crates/security/src/integrity.rs`
- `apps/desktop/src/adapters/secure_storage.rs`

同时 Worker 仍存在占位接口：

- `/api/lease/refresh` → `lease_refresh_pending`
- `/api/task/authorize` → `task_authorize_pending`

#### 风险说明

这会形成“设计能力很强，但运行态执行很弱”的典型错位：

- 离线验签不能真正生效
- 软续约能力无法工作
- 高风险任务未使用 RuntimeGrant
- 完整性失败无法真正阻断业务

#### 整改建议

分阶段接入：

1. 先切换主门禁到 Lease / RuntimeState
2. 再接 `refresh_lease_if_due()`
3. 再接 `authorize_task_local()` 与 Worker `/api/task/authorize`
4. 最后接入完整性校验与 compromised 强阻断

### 4.5 中风险：设备指纹采集与上传存在隐私边界与稳定性问题

**风险等级**: MEDIUM

#### 证据

- `apps/desktop/src/commands/license.rs`
  - 激活时上送 `device_id` + `device_fingerprint`
- `backend/crates/security/src/device_id.rs`
  - 原始硬件标识 / fallback 指纹采集逻辑较完整

#### 风险说明

上传原始设备指纹在产品安全与隐私合规上风险更高，同时也会放大硬件变更、权限受限、系统升级时的误绑定与误判问题。

#### 整改建议

- 优先只上传必要的稳定标识
- 如果必须上传原始设备指纹，建议只上传服务端需要的 hash
- 在产品文档中明确：
  - 采集字段
  - 采集目的
  - 保留周期
  - 用户可见说明

---

### 4.6 中风险：授权域名多活回退提升可用性，但也扩大攻击面

**风险等级**: MEDIUM

#### 证据

- `apps/desktop/src/app_settings.rs`
  - `LICENSE_API_BASE_URLS` 配置了多个域名

#### 风险说明

多域名回退的确提升了可用性，但也会带来：

- 域名治理复杂度上升
- 证书治理复杂度上升
- 域名资产暴露面扩大
- 安全事件响应路径复杂化

#### 整改建议

- 收敛正式域名入口
- 建立域名资产台账
- 做证书与 DNS 监控
- 明确哪些是正式生产授权域名

---

### 4.7 中风险：Tauri 默认 capability 较宽，不利于最小权限治理

**风险等级**: MEDIUM

#### 证据

- `apps/desktop/capabilities/default.json`
  - 当前为 `core:default`

#### 风险说明

随着 IPC 命令增长、WebView 登录能力增强、文件系统访问增多，默认 capability 过宽会使前端注入、IPC 暴露等问题的影响范围扩大。

#### 整改建议

- 按窗口 / 命令 / 场景做最小权限化治理
- 重点收紧：
  - 文件系统
  - 外部 URL
  - Cookie 登录窗口
  - 登录态提取能力

---

### 4.8 低风险：客户端安全事件监控与上报不足

**风险等级**: LOW

#### 证据

- 服务端已具备 `AuditEvent`
- 客户端未见完整的安全事件监控体系

#### 风险说明

没有足够的本地安全事件上报，会导致：

- 用户绕过路径难以追踪
- 授权异常难以定位
- 完整性失败难以感知

#### 整改建议

建议补充以下事件：

- 本地授权材料损坏
- Lease 验签失败
- 设备不匹配
- 续约失败
- Grant 获取失败
- 完整性校验失败
- 多次异常授权尝试

## 5. 功能完整性检查

下面按“授权产品应该具备的能力”检查当前完成度。

| 功能项 | 当前状态 | 结论 |
|---|---|---|
| 卡密激活 | 已具备前后端闭环 | 基本完整 |

> **授权服务基础设施已较完整，但客户端可信执行链尚未完成。**

## 10. 最终结论

从网络安全师 / 产品安全角度看，当前授权系统已经具备比较完整的设计骨架，但仍有一个必须尽快修复的核心问题：

> **客户端当前真正执行授权放行的依据过弱，尚未切换到密码学可验证的 Lease 主链路。**

因此，当前阶段最优先的目标不应继续增加新授权功能，而应优先完成：

- 授权主存储可信化
- 授权门禁可信化
- 授权生命周期闭环化

只有在这三点完成后，现有的离线授权、续约、任务级授权、完整性保护等设计能力，才会真正变成可落地、可依赖的产品安全能力。
