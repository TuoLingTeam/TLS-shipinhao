**项目**: TLS-shipinhao  
**审查范围**: 桌面端授权主链路、授权服务客户端、云端授权服务、离线授权能力、任务级授权能力

## 1. 概述

当前项目的授权体系已经完成主链闭环：

- 桌面端可执行激活、校验、状态读取，并以 RuntimeState 作为授权执法依据
- 云端 Worker 已具备 `/api/activate`、`/api/verify`、`/api/lease/refresh`、`/api/task/authorize`、`/api/lease/revoke`
- `license-service` 已实现卡密、设备绑定、有效期、吊销等核心规则
- 本地已完成 Lease 验签、离线校验、续约、任务级授权、完整性校验、安全存储接入

当前剩余的重点不再是“是否完成强授权闭环”，而是：

> **把 Worker 吊销链的错误契约、回归测试和模块边界继续收尾到可长期维护的状态。**

**总体判断**：授权主链已经闭环，当前进入 Worker 收尾与结构收敛阶段。

## 2. 当前授权链路摘要

当前主链路可概括为：

1. 前端输入卡密，调用 Tauri IPC：`activate_license` / `verify_license`
2. 桌面端采集 `device_id` 与 `device_fingerprint`
3. 通过 `http_license_client.rs` 请求云端授权服务
4. Worker 在 Cloudflare 路径上直接通过 D1 完成：
   - `/api/activate`
   - `/api/verify`
   - `/api/lease/refresh`
   - `/api/task/authorize`
5. 云端返回 `license_state`、`license_expires_at`、`license_lease`
6. 桌面端会先对 `license_lease` 做验签与设备校验，再把 Token 存入安全存储
7. 本地恢复出的 `RuntimeState` 才是后续业务功能的真实门禁依据
8. 高风险任务会进一步请求本地/远端 `RuntimeGrant`

当前真正参与业务门禁的关键对象是：

- `apps/desktop/src/state.rs` 中的：
  - `lease_store`
  - `runtime_license_state`
  - `verify_and_store_license_token()`
- `apps/desktop/src/commands/license.rs` 中的：
  - `ensure_feature_authorized()`
  - `authorize_runtime_task()`

`StoredLicenseProfile` 现在主要承担：

- UI 状态展示
- 最近一次授权摘要缓存
- 兼容旧界面字段

而不再是授权放行的唯一信任根。

已经接入主链路的安全能力包括：

- `backend/crates/license/src/local_verify.rs`
- `backend/crates/license/src/lease.rs`
- `apps/desktop/src/adapters/secure_storage.rs`
- `backend/crates/security/src/integrity.rs`

当前剩余的主要边界已经从“本地明文状态门禁”收缩为：

- Worker 的管理端 `admin_d1.rs` 仍是单独的 D1 管理路径，尚未进一步收敛到统一仓储风格

---

### 4.1 历史高风险（已修复）：本地明文 `license.json` 可被篡改，业务门禁可被绕过

**风险等级**: HIGH

#### 当前状态

该问题已在桌面端整改中完成修复：

- 功能门禁已切换到**验签后的 Lease / RuntimeState**
- `license.json` 不再作为业务放行的信任根
- 启动恢复、在线校验失败回退、任务级授权均已基于 RuntimeState 运行

#### 当前剩余关注点

- 仍需继续保证 UI 缓存字段不会重新回退为执法依据
- 后续变更应维持“信任根只来自验签结果”的约束

**风险等级**: HIGH

#### 当前状态

该问题已在桌面端整改中完成修复：

- `activate / verify` 成功后会真正消费 `license_lease`
- 客户端已执行 Lease 验签、`kind` 校验、`device_id` 校验
- 通过校验的授权材料会进入安全存储，并参与离线门禁

#### 当前剩余关注点

- 仍需保持服务端契约稳定，避免重新退化为裸状态文本
- Worker 侧的错误契约与吊销测试仍需继续收尾

**风险等级**: HIGH

- 主授权材料已切入 `SecretStore`

**风险等级**: HIGH

#### 当前状态

该问题已在桌面端与 Worker 联调中完成主链修复：

- 离线授权验签已进入主链
- 软续约已接通到真实 Worker 路由
- 任务级授权已接入主链并支持远端 RuntimeGrant
- 完整性校验已接入主门禁

#### 当前剩余关注点

- 仍需继续补齐 Worker 吊销相关的错误契约、测试与模块边界
- 续约/任务授权路径的运维配置仍需保障签名密钥与 D1 绑定正确

---

### 4.5 中风险：设备指纹采集与上传存在隐私边界与稳定性问题

**风险等级**: MEDIUM

#### 证据

- `apps/desktop/src/commands/license.rs`
  - 激活时上送 `device_id` + `device_fingerprint`
- `backend/crates/security/src/device_id.rs`
  - 原始硬件标识 / fallback 指纹采集逻辑较完整

#### 风险说明

上传原始设备指纹在产品安全与隐私合规上风险更高，同时也会放大硬件变更、权限受限、系统升级时的误绑定与误判问题。

#### 整改建议

- 优先只上传必要的稳定标识
- 如果必须上传原始设备指纹，建议只上传服务端需要的 hash
- 在产品文档中明确：
  - 采集字段
  - 采集目的
  - 保留周期
  - 用户可见说明

---

### 4.6 中风险：授权域名多活回退提升可用性，但也扩大攻击面

**风险等级**: MEDIUM

#### 证据

- `apps/desktop/src/app_settings.rs`
  - `LICENSE_API_BASE_URLS` 配置了多个域名

#### 风险说明

多域名回退的确提升了可用性，但也会带来：

- 域名治理复杂度上升
- 证书治理复杂度上升
- 域名资产暴露面扩大
- 安全事件响应路径复杂化

#### 整改建议

- 收敛正式域名入口
- 建立域名资产台账
- 做证书与 DNS 监控
- 明确哪些是正式生产授权域名

---

### 4.7 中风险：Tauri 默认 capability 较宽，不利于最小权限治理

**风险等级**: MEDIUM

#### 证据

- `apps/desktop/capabilities/default.json`
  - 当前为 `core:default`

#### 风险说明

随着 IPC 命令增长、WebView 登录能力增强、文件系统访问增多，默认 capability 过宽会使前端注入、IPC 暴露等问题的影响范围扩大。

#### 整改建议

- 按窗口 / 命令 / 场景做最小权限化治理
- 重点收紧：
  - 文件系统
  - 外部 URL
  - Cookie 登录窗口
  - 登录态提取能力

---

### 4.8 低风险：客户端安全事件监控与上报不足

**风险等级**: LOW

#### 证据

- 服务端已具备 `AuditEvent`
- 客户端未见完整的安全事件监控体系

#### 风险说明

没有足够的本地安全事件上报，会导致：

- 用户绕过路径难以追踪
- 授权异常难以定位
- 完整性失败难以感知

#### 整改建议

建议补充以下事件：

- 本地授权材料损坏
- Lease 验签失败
- 设备不匹配
- 续约失败
- Grant 获取失败
- 完整性校验失败
- 多次异常授权尝试

## 10. 最终结论

从网络安全师 / 产品安全角度看，当前授权系统已经具备比较完整的设计骨架，但仍有一个必须尽快修复的核心问题：

> **客户端当前真正执行授权放行的依据过弱，尚未切换到密码学可验证的 Lease 主链路。**

因此，当前阶段最优先的目标不应继续增加新授权功能，而应优先完成：

- 授权主存储可信化
- 授权门禁可信化
- 授权生命周期闭环化

只有在这三点完成后，现有的离线授权、续约、任务级授权、完整性保护等设计能力，才会真正变成可落地、可依赖的产品安全能力。
